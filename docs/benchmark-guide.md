# Методика benchmark — занятие 8

Тот же подход, что на занятии 7: testing.B, b.Run, b.N (Go 1.22), фиксированный seed 7, одинаковые входы, -benchmem и несколько повторов. В измеряемом коде нет fmt.Println. Глобальные sinks, сохранение объектов и runtime.KeepAlive оставляют результат наблюдаемым; итоговые проверки результата идут после StopTimer. Проверки bool/ошибок внутри исходных API-вызовов и некоторых циклов остаются частью измеряемой операции. Интерфейсные вызовы входят в стоимость некоторых моделей.

```bash
make bench-list
make bench-stack
make bench-queue
make bench-hash
make bench-buffer
make bench-memory
make bench-all BENCHTIME=300ms BENCHCOUNT=7 BENCHCPU=1
# Проверка работоспособности всех веток, не скорость:
make bench-smoke
```

По умолчанию 100ms, три повтора, -cpu=1. bench-all вызывает группы последовательно, даже при make -j. Не запускайте параллельно race, сборку, видео, рендеринг и другую benchmark-группу. Подготовка данных с seed и цели исключены из таймера, кроме явно названного build. На входы нет скрытого роста с b.N.

| Группа | Что такое одна op | Предусловия и память |
|---|---|---|
| List search-missing / walk | один поиск отсутствующего значения / один полный обход | n=100/1000/10000; структуры построены, сумма/результат проверяются вне таймера |
| List build-append / build-prepend | вся серия n вставок, включая создание и allocation | n=100/1000; slice заранее выделяет cap=n в таймере, linked выделяет узлы |
| List …-undo / …-restore | вставка+обратное удаление либо удаление+восстановление | обе части в таймере; n=100/1000 постоянно; slice имеет свободный слот |
| List middle-known-undo | InsertAfter/DeleteAfter с готовым handle против известной позиции slice | представление позиции отличается, её поиск исключён у обоих |
| List middle-index-undo | вставка после n/2 с поиском узла через At у list | индекс известен обоим; не называем это O(1) для list |
| Stack | n Push и n Pop, n=32/256 | slice capacity прогрета до ResetTimer; linked узлы каждой серии выделяются внутри |
| Queue | 64 пары Enqueue/Dequeue | длина n=100/1000; ring capacity n+1, все enqueue принимаются; slice-shift — именно O(n) baseline |
| Hash build | все n уникальных string/int пар | n=100/1000/10000; custom и map растут с малого размера, slice не строит индекс |
| Hash lookup | один готовый поиск last/missing | подготовка исключена, длина ключа ограничена и одинакова; last означает позицию в slice |
| Hash insert-read-delete | тройка операций с новым заведомо отсутствующим ключом | размер восстанавливается, чтение результата есть у всех; в slice найденный индекс используется для удаления |
| Hash delete-restore | удалить существующую пару и снова добавить её | восстановление внутри таймера; custom повторно выделяет entry |
| Buffer accumulate | собрать n фрагментов, n=100/1000, в новый объект | проверка байтов и копия Bytes нашей Linear исключены; глобальный sink сохраняет последнюю структуру |
| Buffer ring-cyclic | 64 пары записи/чтения в bounded ring | capacity=32/1024, другая семантика: не накапливает весь поток |
| Memory | построить n элементов | slice, singly, стандартный container/list; n=100/1000/10000; allocation измеряется, не retained heap |

Формат результатов: ns/op, B/op, allocs/op. B/op — суммарные выделения heap на тело, не весь размер удерживаемой структуры. Если ring создан до таймера, 0 B/op не отменяет O(cap) памяти. Call stack и ранее выделенный backing array так не измеряются. Retained heap здесь отдельно не измерялся: для него нужен отдельный процесс, контроль времени жизни/GC и heap profiles, а не вычитание случайных MemStats во время другого benchmark.

Медиана A/B показывает, во сколько раз B быстрее A на этой машине, при одинаковом n/сценарии/границах. Смотрите min/max и увеличивайте длительность/повторы. Benchmark не доказывает Big O. Для функции hash нужна предпосылка распределения, для slice append — амортизация, для list insert — известный handle. Универсального победителя из таблицы не следует.

[Реальные замеры](benchmarks/README.md) содержат все 112 сценариев × 3 повтора. Источник определения таймеров и allocation: [testing Go 1.22](https://github.com/golang/go/blob/go1.22.12/src/testing/benchmark.go).

## Сводка, единицы и фильтры

У всех шести `make bench-*` одинаковый формат: отдельные таблицы по операции и численному `n` / `chunks` / `cap`. Строки разных CPU/GOMAXPROCS и окружений не смешиваются. Размеры упорядочены численно: 100, 1000, 10000. Время автоматически показано в ns/µs/ms/s, выделения — B/KiB/MiB/GiB; в CSV остаются исходные ns и B. Таблица показывает медиану, минимум и максимум времени; min/max помогают увидеть разброс коротких прогонов.

По умолчанию выводится **медиана**, не среднее. Для каждого сценария берутся равноправные результаты повторов `-count`, затем медиана, арифметическое среднее и min/max. При чётном числе повторов медиана — среднее двух центральных значений. `b.N` не используется как вес. CSV хранит все эти агрегаты отдельно для времени, выделенных байтов и количества allocation (min/max относятся ко времени). Одного прогона недостаточно, чтобы судить о разбросе.

В raw строка `Benchmark…  <b.N>  <ns/op> …` содержит число итераций, выбранное Go. Имя `n=1000` описывает данные. `-count=3` повторяет весь сценарий трижды. Это три разных числа.

```bash
make bench-list BENCHSIZE=1000 BENCHOP=middle-index-undo
make bench-list BENCHVIEW=full
make bench-hash BENCHOP=lookup-missing BENCHCPU=1,2
make bench-buffer BENCHSIZE=1000 BENCHOP=accumulate
make bench-buffer BENCHSIZE=32 BENCHOP=ring-cyclic-64-pairs
make bench-memory-raw
make bench-all-raw BENCHTIME=20ms BENCHCOUNT=3
```

`BENCHSIZE=0` означает все размеры существующей матрицы. Неизвестная операция или размер без результатов — ошибка, а не пустая «успешная» таблица. Режим compact сокращает терминальный вывод List/Hash, явно сообщает число скрытых строк; raw/CSV всегда полные. `BENCHVIEW=full` показывает всё. `bench` — псевдоним `bench-all`; шесть `*-raw` выводят исходные строки, `bench-all-raw` запускает их последовательно.

Каждый запуск создаёт отдельный каталог в `BENCHDIR` (по умолчанию `bin/benchmarks`). `raw.txt` сохраняется даже при сбое процесса. Успешный разбор требует полного вывода `go test` с окружением, PASS и финальным ok. CLI и parser проверены на обрезанных строках, ошибочных метриках, неполных повторах и провалившемся процессе. Не объединяйте несколько самостоятельных raw-логов простым `cat`.

Можно заново отформатировать один готовый лог:

```bash
go run ./cmd/benchreport -kind list -input /absolute/path/raw.txt -count 3 -view full
```

При импорте версия Go и параметры таймера неизвестны из raw и честно помечены как неизвестные; сохраните исходный `environment.json` рядом. Произвольный raw другой лаборатории этот parser не поддерживает.

## Память и корректное сравнение

Под таблицами показана приблизительная полезная нагрузка: `n × sizeof(int)` для целых, 16 байт на фрагмент Buffer, слоты byte для ring, длина ключей и int-значения для Hash. Это **не** полная память контейнера: указатели, headers, buckets, запас capacity, allocator и временные объекты сюда не входят. Размер int зависит от GOARCH.

Поиск отсутствующего значения в готовых list/slice и lookup одинакового ключа можно сравнивать при одном контракте. Hash build у slice означает создание пар без индекса: объявлять его «более быстрым индексом» нельзя. Memory сравнивает allocation при построении структур с разными возможностями. Накопительный Buffer и bounded ring решают разные задачи. Автоматический коэффициент скорости для таких групп намеренно не выводится. Для сопоставимых сценариев коэффициент — отношение медиан одного компьютера, не универсальное свойство структуры.

Для измерений без отладчика/`-race` закройте анимацию и прочую нагрузку. Результаты `1x` в CI нужны только для проверки выполнения всех веток. Они не используются для учебных выводов о скорости и не являются порогом CI.
